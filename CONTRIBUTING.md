# Contributing to Embedded-IoT Curriculum

Thank you for your interest in contributing to this embedded systems and IoT curriculum!

## Contribution Philosophy

This curriculum is designed to be:
- **Practical** - Focus on building real systems
- **Progressive** - Build understanding step-by-step
- **Accurate** - Technical correctness is paramount
- **Beginner-friendly** - Accessible to those with no prior experience
- **Assessment-driven** - Prove competence before advancing

## Types of Contributions

### Content Contributions
- New phase content (when gaps are identified)
- Lab improvements and additions
- Project implementations
- Assessment questions and tests
- Documentation improvements
- Resource additions

### Code Contributions
- Working project implementations
- Example code improvements
- Bug fixes in example code
- Additional project variants
- Code optimization (with explanations)

### Documentation Contributions
- README improvements
- Clarification of complex topics
- Additional troubleshooting steps
- Hardware compatibility notes
- Translation (if maintaining language parity)

### Resource Contributions
- Links to high-quality free resources
- Official documentation references
- Alternative learning materials
- Hardware substitution guides

## Contribution Guidelines

### Before Contributing

1. **Understand the Curriculum Structure**
   - Read the main README.md
   - Review ROADMAP.md
   - Understand the learning philosophy
   - Check existing content structure

2. **Identify Gaps**
   - Look for incomplete phases
   - Check for missing labs/projects
   - Identify unclear explanations
   - Find broken or missing resources

3. **Check Existing Issues**
   - Review GitHub issues
   - See if someone is already working on it
   - Comment on existing issues before starting

### Content Standards

#### Quality Requirements
- **Accuracy:** All technical content must be accurate
- **Clarity:** Explanations must be clear and progressive
- **Completeness:** Include all required sections (see Phase Template)
- **Testing:** Code must be tested on actual hardware when possible
- **Safety:** Include safety warnings for electrical work

#### Structure Requirements
Each phase must include:
1. Goal
2. Prerequisites
3. Learning outcomes
4. Concepts
5. Exact study order
6. Exact resources
7. Exercises
8. Practical labs
9. Debugging exercises
10. Project(s)
11. Common mistakes
12. Troubleshooting
13. Knowledge assessment
14. Practical assessment
15. Completion checklist
16. "Do not continue until..." gate
17. Next phase

#### Writing Style
- Be concise and direct
- Avoid jargon without explanation
- Use active voice
- Include practical examples
- Explain WHY, not just HOW
- Assume no prior knowledge for early phases

### Code Standards

#### Code Quality
- Follow language conventions (C, Python, etc.)
- Include meaningful comments
- Use clear variable/function names
- Handle errors appropriately
- Include error messages for debugging

#### Code Structure
- Modular organization
- Separate concerns
- Include header comments explaining purpose
- Document complex algorithms
- Include compilation/build instructions

#### Testing
- Test on actual hardware when possible
- Note if code is untested
- Include expected output/behavior
- Document known limitations

### Documentation Standards

#### README Files
- Clear purpose statement
- Prerequisites section
- Step-by-step instructions
- Troubleshooting section
- Next steps

#### Code Documentation
- Function headers with purpose
- Parameter descriptions
- Return value descriptions
- Usage examples
- Error conditions

#### Hardware Documentation
- Clear wiring diagrams
- Component specifications
- Safety warnings
- Power requirements
- Testing procedures

## Contribution Process

### For Small Contributions

1. Fork the repository
2. Create a feature branch
3. Make your changes
4. Test your changes
5. Submit a pull request with description

### For Content Contributions

1. **Propose First**
   - Open an issue describing your planned contribution
   - Get feedback on approach and scope
   - Coordinate with maintainers

2. **Develop Content**
   - Follow the phase template
   - Include all required sections
   - Test exercises and labs
   - Verify resource links

3. **Submit for Review**
   - Create pull request
   - Describe what you've added
   - Explain how it fits the curriculum
   - Request specific feedback

### For Project Contributions

1. **Follow Project Structure**
   ```
   project-name/
   ├── README.md
   ├── circuit/
   │   ├── schematic.png
   │   └── wiring.md
   ├── src/
   ├── tests/
   ├── docs/
   └── results/
   ```

2. **Include Required Elements**
   - Complete README with objectives
   - Circuit documentation
   - Working source code
   - Build instructions
   - Testing procedures
   - Results/observations

### For Resource Contributions

1. **Verify Resource Quality**
   - Check it's from an official/reputable source
   - Verify it's freely accessible
   - Confirm it's technically accurate
   - Ensure it's relevant to curriculum

2. **Add to Resource Index**
   - Update RESOURCE_INDEX.md
   - Include all required fields
   - Follow the table format
   - Categorize appropriately

## Review Process

### What Reviewers Check
- Technical accuracy
- Clarity and completeness
- Fit with curriculum structure
- Progressive difficulty
- Safety considerations
- Resource validity
- Code quality and testing

### Feedback Types
- **Required Changes:** Must be addressed before merge
- **Suggested Changes:** Recommendations for improvement
- **Clarification Questions:** Requests for more information
- **Approval:** Ready to merge

### Iteration
- Address feedback systematically
- Respond to each comment
- Explain your decisions
- Request re-review when ready

## Testing Requirements

### Content Testing
- Follow your own instructions
- Verify all steps work
- Check all links are valid
- Ensure resources are accessible

### Code Testing
- Compile/build successfully
- Run on target hardware when possible
- Test all documented features
- Verify error handling

### Hardware Testing
- Build circuits as documented
- Verify component specifications
- Test safety procedures
- Measure actual behavior

## Style Guidelines

### Formatting
- Use Markdown for documentation
- Follow existing formatting patterns
- Use code blocks for code
- Use tables for structured data
- Use headings for organization

### Terminology
- Use consistent terminology
- Define technical terms on first use
- Avoid acronyms without explanation
- Use industry-standard terms

### Tone
- Professional and educational
- Encouraging and supportive
- Precise and accurate
- Avoid unnecessary complexity

## What Not to Contribute

### Avoid
- Copyrighted material without permission
- Links to paywalled content as primary resources
- Untested code without clear warnings
- Incomplete phases without discussion
- Redundant content
- Vendor-specific content without alternatives

### Specifically
- Don't redistribute copyrighted books/PDFs
- Don't add promotional content
- Don't include affiliate links
- Don't add platform-specific content without alternatives
- Don't break the progressive learning structure

## Large Contributions

For substantial contributions (new phases, major rewrites):

1. **Discuss First**
   - Open an issue with proposal
   - Get consensus on approach
   - Plan integration points
   - Define scope clearly

2. **Iterative Development**
   - Work in manageable chunks
   - Submit incremental PRs
   - Get feedback early and often
   - Adjust based on reviews

3. **Documentation**
   - Document your decisions
   - Explain trade-offs
   - Provide context for changes
   - Update related documentation

## Questions and Support
